SRS Document

Weight: 30%

File: SRS_full.txt — 426 lines covering the complete Software Requirements Specification for ShopFlow, our electronics e-commerce platform.

What Our SRS Covers

  • Purpose: A semester-long web development project demonstrating full-stack capabilities — not a commercial product, but a functional, demo-ready system
  • Scope: Product catalog with search/filter, shopping cart, checkout with payment screenshot upload, user accounts, order history, multi-tier admin roles, reviews/ratings, wishlist, and in-app price-drop notifications
  • Stakeholders: Instructor (evaluator), customers (classmates/testers), administrators (Theara & Youpheng)
  • Functional Requirements: Product browsing & filtering, cart & checkout, user account management (including wishlist and address editing), payment via KHQR screenshot upload, admin order/product/user management, superadmin full control
  • Non-Functional Requirements: Responsive mobile design, dark/light theme, loading skeletons for UX, modern browser compatibility
  • Constraints: Free hosting (Render), free cloud database (Neon PostgreSQL), free image storage (Cloudinary), no real payment processing, team of 2, one-semester timeline

Evolution from Original SRS

Original spec: Simple product catalog + cart + checkout. What we actually built: Everything in the original, plus reviews/ratings system with star picker, wishlist with price-drop notifications, multi-tier admin roles (admin + superadmin), stock tracking with management UI, color + screen size + brand + price + rating filters (all collapsible), profile editing with Cloudinary avatar upload, related products engine, in-app notification bell with badge count, dark/light theme toggle, full analytics dashboard with Chart.js, and 11 HTML pages with responsive mobile layout.

The SRS document was our roadmap — it defined the initial scope, and we documented scope changes as we expanded the project during development.

Planning Approach

  • MVP first: Started with the minimum viable product (browse, cart, checkout) as defined in the SRS
  • Iterative enhancement: Added one feature group at a time — filters, then reviews, then wishlist, then notifications, etc.
  • Git commits as milestones: Each development session produced a batch of related commits, serving as our progress tracker
  • User-driven priorities: We prioritized features that would be most visible during the demo (UI polish, animations, dark theme)

Database Structure

Weight: 10%

Database: PostgreSQL 16 hosted on Neon cloud. File: database.js — 131 lines handling pool connection, table creation, and seed data.

Entity Relationship Diagram

┌─────────────────────────────────────────────────────────────────────────────┐ │ DATABASE SCHEMA │ ├─────────────────────────────────────────────────────────────────────────────┤ │ │ users products ───────────── ───────────── id (PK, TEXT) id (PK, INTEGER) firstName name lastName brand email (UNIQUE) category password price role (customer/admin/superadmin) originalPrice createdAt discount avatar description address specs (JSON text) phone colors (JSON text) │ rating │ reviews │ inStock │ featured │ section │ image ▼ stock orders reviews ───────────── ───────────── id (PK, TEXT) id (PK, SERIAL) userId (FK → users) productId (FK → products) customerName userId customerEmail userName subtotal avatar tax rating (1-5) shipping comment total createdAt shippingInfo (JSON text) updatedAt paymentScreenshot (URL) │ status │ createdAt │ approvedBy │ approvedAt (reviews belongs to user + product) │ ▼ order_items ───────────── id (PK, SERIAL) orderId (FK → orders) productId name price quantity selectedColor selectedStorage └─────────────────────────────────────────────────────────────────────────────┘

Tables Overview

Table Primary Key Foreign Keys Key Columns
users id (TEXT) — firstName, lastName, email (UNIQUE), password, role, avatar, address, phone
products id (INTEGER) — name, brand, category, price, originalPrice, discount, specs, colors, rating, reviews, stock, image
reviews id (SERIAL) productId → products, userId → users rating (1-5), comment, avatar, createdAt, updatedAt
orders id (TEXT) userId → users subtotal, tax, shipping, total, shippingInfo, paymentScreenshot, status, approvedBy
order_items id (SERIAL) orderId → orders productId, name, price, quantity, selectedColor, selectedStorage

Key Design Decisions

  • Manual INTEGER IDs for products: Allows predictable seeding of 30 products with consistent IDs across environments
  • TEXT IDs for orders: Format ORD-{timestamp}-{random} for readability and uniqueness
  • JSON text for complex fields: specs (display, processor, RAM, storage, battery) and colors stored as JSON strings — parsed on the client side
  • Rating auto-calculation: Product rating is recalculated via SELECT AVG(rating) on every review add/edit/delete — no stale data
  • ALTER TABLE migrations: New columns (avatar, address, phone, stock, approvedBy, approvedAt) added via ALTER TABLE with IF NOT EXISTS, allowing safe schema evolution on the deployed database without data loss
  • shippingInfo as JSON: Flexible address fields (street, city, zip, country) stored as a single JSON text column

Deployment Setup

  • Platform: Render.com — free tier, auto-deploys from GitHub on every push to main branch
  • Node version: 20.x (LTS) — pinned in package.json via "engines": { "node": "20.x" }
  • Build command: npm install
  • Start command: node server.js
  • Database initialization: On first startup, database.js creates all tables (IF NOT EXISTS), runs ALTER TABLE migrations for new columns, and seeds 5 admin/superadmin users

Why These Services

Service Why We Chose It
Render Free hosting with automatic HTTPS/SSL, auto-deploy from GitHub, no credit card required for free tier, handles Node.js apps natively
Neon (PostgreSQL) Free cloud PostgreSQL with 500MB storage, persists data across server restarts (Render spins down after inactivity — Neon keeps data safe), standard SQL compatibility
Cloudinary Free tier (25GB storage, 25GB bandwidth), automatic image optimization, URLs persist permanently (unlike local /uploads directory which would be deleted on every Render redeploy)
GitHub Free private/public repos, webhook integration with Render for seamless CI/CD
Important: Cloudinary is critical for this project. Because Render's filesystem is ephemeral (any file saved to disk disappears when the server restarts or redeploys), we store all images (product images, payment screenshots, user avatars) on Cloudinary. This guarantees data persistence across server restarts and redeployments. Environment variables are configured in Render's dashboard, never committed to the repository.
